# 设计说明

## 问题和取舍

业务资料中的金额、阶段和客户反馈常混在自然语言里。直接让模型写周报，容易把未经确认的转述变为事实，或把测试和合同、在途金额和预测混为一谈。

本项目先由本地代码完成明确的检查和汇总，再把相同输入和检查结果交给AI辅助分析。六模块共享同一份只读数据，结构化检查结果及AI任务包携带输入指纹。最终交付仍需人工复核，不由模型执行外部动作。

## 处理顺序

1. **输入校验**：JSON版本、金额精度、阶段枚举、日期、唯一ID及来源归属；不合格输入在写文件前退出。
2. **字段冲突检查**：同一商机同一字段出现不同来源值，或来源值与记录值不一致时，整条记录暂缓汇总。不自动采纳最新来源。
3. **确认门槛**：记录、来源均已确认；已签约还必须有合同确认标记。未知预算可以作为“已记录但预算待确认的机会”出现，不能因此成为预测。
4. **口径化汇总**：仅已确认的discovery、validation、negotiation进入在途；won单独统计；lost和cancelled保留历史但不计入在途。
5. **任务输出**：按模块生成报告和AI任务包。报告由规则生成，提示词等待用户手动交给已授权模型。
6. **草稿复核**：校验模型JSON中的商机、来源、阶段及金额，再由人检查自由文本及动作可行性。

## 模块之间如何协作

总控只分派问题，不修改业务金额；渠道模块解释伙伴经营范围，不发明客户成果；商机检查负责暴露冲突；周报只引用可汇总事实；方案模块提出待确认的验证清单；知识模块保留来源和有效期，不改变项目状态。

当前实现是同一进程内的函数与文档边界，没有自主Agent调度、后台任务、模型记忆或向量数据库。知识搜索使用关键词匹配，不是RAG。不存在自动写回CRM、发邮件或客户系统集成。

## 为什么需要人工确认

代码可以检查“引用是否存在、金额是否一致”，但不能知道客户有没有改变主意，也不能完全理解来源文本是否支持某个复杂结论。confirmed是演示输入中的人工标签，不是算法给事实背书。

check_draft只验证facts数组的结构化字段。actions、open_questions、knowledge_notes和statement的完整语义不属于自动验证范围。即使校验通过，也不能直接外发。

## 只读与安全

- analyze不修改输入对象；本地命令不联网、不读取凭据、不扫描父目录。
- demo只写入用户指定的新目录，不覆盖已有目录。
- HTML对输入文本转义，页面无外部脚本或字体。
- 来源中的指令作为文本处理；对外部模型的提示注入抵抗能力未通过模型实测。
- 公开版不复制企业资料；发布只使用publication.json内的白名单文件。

## 后续可扩展但尚未实现

外部模型API适配、Excel导入、人工审批界面、多用户权限、持久化台账和跨版本变更比较均未实现。本次公开版不把它们写成现成功能。
